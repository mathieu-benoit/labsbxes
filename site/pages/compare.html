Before · labspace-infra

docker compose up

Six containers share your host's Docker engine. The learner's docker reaches that engine through socket-proxy, which labels, filters and remaps every call so the lab only sees, mounts and later deletes its own resources.

  • A configurator clones the content repo into volumes
  • host-port-republisher bridges the learner's ports to localhost
  • workspace-cleaner removes labeled resources on down
After · this repo

sbx run

One Docker Sandbox per lab: a microVM with its own kernel and its own Docker engine. The lab is composed from kits: the shell workload, the Labspace kit, and optionally a content kit.

  • The lab is a folder, a content kit, or the built-in getting-started lab
  • The runtime publishes the ports the kits declare (port@1)
  • sbx rm deletes the VM and everything the lab created

What stays the same for lab authors

A lab keeps the labspace-infra layout, labspace/ (labspace.yaml and the markdown) and project/ (what the IDE opens), so existing content runs as is. To hand a lab to someone, add two small files and it becomes a content kit, like the Building Container Images lab, which is dockersamples/labspace-building-images unchanged.

Trade-offs to know

  • Pin the IDE port. The interface embeds the IDE at http://localhost:8085, so every run pins -p 8085:8085, and only one lab at a time can use it.
  • The project lives in the sandbox. With a content kit, the learner's edits survive sbx stop but not sbx rm.
  • Start from an empty folder. The folder sbx run starts in is mounted into the sandbox, so never start from your home directory.
  • Instructions are not read-only. labspace-infra mounted them read-only; in a sandbox the learner owns the VM anyway.

Diagrams of both setups are in docs/architecture.md. The original stack is dockersamples/labspace-infra.
